# AGENTS.md — erp_lite

> Глобальные правила машины — в `~/.dsh/AGENTS.md`, они применяются автоматически.
> Этот файл дополняет их и имеет приоритет в каталоге проекта.

## 0. Что это за проект и что в него НЕ входит

`erp_lite` — **намеренно лёгкое** приложение для пяти ролей: **Менеджер по продажам**,
**Коммерческий директор**, **Директор по закупкам**, **Менеджер по закупкам (импорт)**,
**Исполнительный директор** (аналог ген. директора). Политика изменилась: универсального
ERP больше не строим.

**Зона 1С (не дублировать здесь):** производство, склады, внешние интеграции,
бухгалтерия, счета и проводки, курсовые разницы. Данные приходят выгрузками
(`.xlsx`) либо вводятся вручную.

**Зона `erp_lite`:** партии и остатки с оперативной себестоимостью, планирование
продаж → закупок, матрица ценообразования, PnL / Cashflow, таск-трекер, RBAC
(вход и пять ролей уже есть).

Меню разделов сгруппировано по категориям (раскрываются по стрелке, открыта одна):
**Планирование** (продажи, закупки, матрица цен) · **Закупки** (поступления,
поставщики) · **Справочники** (номенклатура, контрагенты, валюты, страны) · **Отчёты**
(остатки, PnL / Cashflow) · **Задачи** · **Администрирование** (загрузка данных,
пользователи, настройки).

Предыдущий проект (`/mnt/extraspace/erp_v_2`, форк `custom_erp`) — **справочник**.
Он не запускается и не изменяется; из него перенесена только оперативная формула
себестоимости. Бухгалтерский слой себестоимости сознательно **не** переносился.

## 2. Команды

```sh
docker compose up -d --wait          # PostgreSQL проекта (проверяет healthcheck)

cd backend
make install                         # venv на python3.12 + зависимости (один раз)
make db-bootstrap                    # схема (create_all) — пока миграций нет
make run                             # API на 127.0.0.1:4111
make check                           # ВОРОТА: ruff format --check + ruff check + mypy + pytest
make test                            # только pytest

cd frontend
pnpm install                         # один раз
pnpm dev                             # UI на 127.0.0.1:4110 (проксирует /api → 4111)
pnpm typecheck && pnpm lint && pnpm test && pnpm e2e && pnpm build
```

## 3. База данных

- Своего контейнера и тома хватает: **не подключаться** к БД других проектов.
- `pytest` в `conftest.py` делает `drop_all/create_all` по `TEST_DATABASE_URL`
  (`erp_lite_test`). Никогда не подставлять сюда рабочую или чужую базу.
- Alembic подключён как зависимость, но история миграций **пока пустая**: схема
  создаётся `Base.metadata.create_all` (`make db-bootstrap`). Первую миграцию
  заводим в тот момент, когда схема перестанет быть одноразовой, и с этого
  момента `create_all` для основной базы не используем.

## 4. Правила кода и данных

1. **Деньги — только `Numeric`/`Decimal`.** `Float` в финансовых полях запрещён;
   pre-commit-хук это блокирует. В JSON деньги уходят **строкой** (точность не теряется).
2. Оперативная формула себестоимости живёт в одном месте —
   [`backend/app/services/cost.py`](backend/app/services/cost.py). Менять её —
   только с обоснованием и тестами на векторах из `erp_v_2`.
3. Изменения денежной логики, схемы данных и форматов выгрузок 1С — **SLOW TRACK**:
   сначала согласование контракта данных, потом код.
4. Секреты — только в `.env` (в git не попадает); ключи не логировать.
5. Сами файлы выгрузок 1С в git не кладём — каталог `data/` в `.gitignore`.

## 5. Чек-лист «готово»

1. `cd backend && make check` → зелёный.
2. `cd frontend && pnpm typecheck && pnpm lint && pnpm test && pnpm build` → зелёные.
3. Для изменений интерфейса — `pnpm e2e` и реальная проверка UI (skill `web-ui-verify`).
4. В отчёте перечислено, что **не** проверено.
5. Коммит — conventional (`feat|fix|refactor|test|chore|docs`), мелкий и осмысленный.

Корректировка планов — полная копия (2026-10-23):

- Backend: `make check` зелёный — `pytest` **151 passed** (4 новых сценария: полная копия
  с добавлением/удалением позиций, коммерческий директор создаёт и применяет,
  исполнительный директор предлагает, но не утверждает, замороженные месяцы не трогаются).
- Frontend: typecheck, lint, **83 unit-теста**, **16 e2e**, сборка — зелёные.
- Корректировка утверждённого плана менеджера переработана: это **полная
  редактируемая копия** строк плана на редактируемые месяцы, а не список точечных
  изменений. В черновике сразу лежат все строки плана; можно менять объёмы,
  добавлять и удалять клиентов, товары и позиции. При утверждении строки
  редактируемых месяцев заменяются целиком (замороженные месяцы не трогаются),
  план остаётся утверждённым, годовой план уходит в `revision`.
- Создать корректировку может владелец-менеджер, **коммерческий директор** (любого
  утверждённого плана) и **исполнительный директор** (предложить корректировку).
  Все трое могут править черновик; коммерческий директор может править черновик
  менеджера. Отправляет черновик любой из них, **утверждает только коммерческий
  директор**. Применить без отправки нельзя — проверено и на сервере, и тестом.
- В интерфейсе утверждённый план read-only для всех (кнопки «Сохранить» нет):
  правка идёт только через блок корректировки. При открытом черновике основная
  таблица плана скрыта, чтобы не дублировать сетку; после отправки показывается
  «было/стало» и таблица текущего плана. Кнопка «Убрать» у позиции не даёт удалить
  строку с замороженными месяцами.
- Замороженные месяцы по-прежнему менять нельзя (ни менеджеру, ни коммерческому,
  ни ГД); корректировка их не копирует и не применяет. Старые корректировки,
  хранившие только изменения, сервер по-прежнему применяет как точечный патч —
  обратная совместимость по набору ключей.
- UI корректировки: полная сетка клиент × товар × месяц, добавление/удаление
  клиентов и позиций, живой счётчик «изменено строк», «было/стало» только по
  изменённым строкам. На 1280 px таблица помещается (замер `scrollWidth =
  clientWidth`), длинные названия из 1С переносятся, а не обрезаются.
- Подсказка после применения корректировки перестала быть статичной: сервер отдаёт
  `annual_needs_reapproval`, и фраза про повторное согласование показывается только
  пока годовой план действительно ждёт его. После повторного утверждения ГД остаётся
  только «Изменения применены к плану». Проверено на живом стенде 2026 (корректировка
  утверждена, годовой план согласован заново); скриншот
  `artifacts/ui/correction-settled.png`.
- Живой стенд (2027, 2026 не тронут): создан утверждённый план sales с двумя
  позициями; в UI коммерческий директор создал корректировку, изменил объём, сохранил,
  отправил и утвердил; API-прогон отдельно проверил добавление и удаление позиции.
  После проверки планы, строки и корректировки 2027 удалены.
  Скриншоты — `artifacts/ui/correction-editor.png` (полная сетка) и
  `artifacts/ui/correction-diff.png` (было/стало); vision-проверка: обрезок,
  наложений и горизонтального выезда страницы нет. Попутно e2e-даты переведены на
  локальный формат (UTC-`toISOString` сдвигал день около полуночи).
- Не проверено: одновременная правка одной корректировки двумя пользователями;
  20+ позиций с длинными названиями на 1280 px (проверено на двух позициях);
  замороженные месяцы в UI живого стенда (правило покрыто тестами); сценарий
