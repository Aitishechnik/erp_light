# Аудит: планирование и распределение сырья по позициям

Дата: 2026-11-01. Область: годовой план продаж → план закупок сырья → поступления →
расчёт потребности, покрытия и альтернатив. Код не менялся, это только аудит.

Отдельной сущности «заказ» в коде нет: источник потребности — утверждённый годовой
план продаж, а «заказ» в интерфейсе — это рассчитанный месяц заказа строки плана
закупок. Если под «заказами» имеются в виду заказы клиентов, их в этом модуле нет.

## Коротко

- **Простое распределение работает:** если у нескольких позиций одного сырья есть
  потребность **в одном и том же месяце**, приход делится между ними, сначала тратится
  основное сырьё, альтернатива — только на нехватку.
- **Требование 1 выполнено частично.** Общий котёл не переносит остаток одной позиции
  на другую, если у той в этом месяце нет потребности. Плановый объём основного сырья
  между продуктами автоматически не распределяется — количества вводятся вручную.
- **Требование 2 не выполнено в двух ключевых местах.** Новые поступления не
  подхватываются автоматически (нужна ручная привязка), а приход в месяц без
  потребности вообще не участвует в покрытии. При удалении основной строки
  альтернативы удаляются, а не заменяют её.
- **Требование 3:** есть критичные дефекты целостности — молчаливая потеря привязки
  поступления при удалении альтернативы и потеря правок при одновременном сохранении
  двумя пользователями.

Проверено фактическим прогоном: backend `make check` — **209 тестов**, frontend
`pnpm test` — **113 тестов**, плюс отдельные временные проверки на тестовой БД
(после проверки удалены). Не проверено: живой интерфейс/e2e, реальные данные 1С,
нагрузка и одновременная работа нескольких пользователей в браузере.

## 1. Что уже работает

- План закупок создаётся только при финально согласованном годовом плане продаж;
  позиции и месяцы берутся из него.
- Годовое количество строки раскладывается по месяцам пропорционально продажам
  позиции; остаток округления отдаётся последнему месяцу, сумма сходится.
- Месяц заказа сдвигается на срок доставки страны; дата может уйти в предыдущий год.
- Статусы `draft → on_review → approved`, роли, возврат на доработку, пересмотр
  источника и «принять к сведению» реализованы.
- У строк постоянный `id`; связанную с поступлением строку нельзя удалить или сменить
  у неё сырьё/страну/позицию (409) — для **основных** строк это работает.
- Факт считается по явным привязкам поступлений и раскладывается по месяцу прихода.
- В одном месяце, если у строк есть потребность, приход общего сырья делится между
  позициями пропорционально потребности; основное сырьё тратится раньше альтернативы.
- `SELECT … FOR UPDATE` на плане сериализует правку, отправку, утверждение и привязку
  поступления; «смеси двух версий» в одной строке нет.

## 2. Требования 1 и 2: где расходится

### 2.1. Основное сырьё и «потребность по продуктам»

В справочнике нет признака «основное сырьё для продукта» и нет норм расхода/BOM.
«Основная» — это любая строка плана без `alternative_of_id`; альтернатива — строка,
которая ссылается на неё. Поэтому:

- программа не знает, что пришедшее сырьё является основным **для конкретной
  продукции**; это определяется только вручную созданной строкой плана;
- плановый объём основного сырья между готовыми продуктами **не распределяется
  автоматически**: закупщик вводит годовое количество в каждую строку;
- распределяются только **приходы** (и то с оговорками ниже), а не плановый объём.

Если у одного сырья несколько позиций, для каждой нужна своя строка с количеством.
Если строку для позиции не завели, её потребность в плане вообще не представлена.

### 2.2. Приходы не появляются в плане автоматически

Привязка поступления к строке плана — **ручная** (это зафиксировано в контракте
поступлений): 1С не знает план, по умолчанию строка «не по плану». Пока закупщик не
поставил привязку, приход не влияет ни на факт, ни на покрытие. Кроме того:

- в карточке предлагаются только строки **утверждённого** плана;
- загрузка позиций файлом «Партия» пересоздаёт строки и **снимает привязки**;
- заголовок поступления из 1С приходит без позиций — их добавляют вручную или файлом.

То есть «как только сырьё появилось в Поступлениях» на практике не наступает:
появление — это несколько ручных шагов, а без привязки приход для плана не существует.

### 2.3. Замена основным сырьём работает только в узком случае

Внутри месяца основное сырьё действительно тратится раньше альтернативы. Но замена
не происходит, если:

- приход основного сырья попал в месяц, которого нет в графике потребности
  (см. 3.1);
- у строки основного сырья в этом месяце нет потребности, а потребность есть у
  другой позиции (см. 3.2);
- приход не привязан к плану (см. 2.2);
- основное сырьё пришло позже месяца потребности — задним числом оно не заменяет
  уже израсходованную альтернативу (это физически нормально, но в отчёте это не
  объясняется).

При этом **план закупки альтернативы не меняется**: уменьшается только
`used_quantity` в расчёте покрытия. Строка альтернативы остаётся с прежним
количеством; закупщик должен сам увидеть, что она больше не нужна, и уменьшить её.
Автоматического перераспределения плана нет.

### 2.4. Обратной замены нет

Если основную строку убрать из плана, её альтернативы **удаляются вместе с ней** —
и в интерфейсе (кнопка «×» убирает и альтернативы), и на сервере. Альтернатива не
становится основной и не продолжает закрывать потребность. Требование «убрали
основное — на период потребности его заменяет альтернатива» в текущей модели
невыполнимо: альтернатива не существует без основной строки.

Если понимать «убрали основное» как «удалили/отвязали приход основного сырья», то
альтернатива пересчитывается и закрывает нехватку — но с теми же оговорками 3.1–3.2.

## 3. Критичные ошибки

### 3.1. Приход в месяц без потребности исчезает из покрытия

Расчёт перебирает только месяцы, в которых у основных строк есть потребность
(`month_rows`). Приходы за другие месяцы в котёл не добавляются. Поэтому:

- приход в январе при потребности только в марте — не учитывается;
- приход между двумя месяцами потребности (январь и март, приход в феврале) —
  не учитывается;
- приход после последнего месяца потребности — не учитывается;
- приход в декабре предыдущего года, который по правилу относится к январю, тоже
  теряется, если январской потребности нет.

При этом в `fact_quantity` и в подписи «пришло» он есть. Получается противоречие:
«пришло 12», «перекрыто 0 из 30», «докупить 30», а излишек равен нулю.

Пример из существующего теста: план на январь–февраль, поступление в марте. Тест
проверяет только `fact_quantity`, поэтому дефект не ловится. В интерфейсе такой
приход показывается как «вне графика», но покрытие не уменьшает.

### 3.2. Общий котёл не переносит остаток на другую позицию

В месяце `taken` суммирует наличие только тех основных строк, у которых **в этом
месяце есть потребность**. Строка с запасом, но без потребности в этом месяце, в
расчёте не участвует. Пример:

- позиция A: 10 кг в январе; позиция B: 10 кг в феврале;
- приход 20 кг на A в январе.

Январь: A закрыта, излишек 10. Февраль: B — «докупить 10», при этом «излишек 10»
показывается одновременно. Общий котёл должен был закрыть B из остатка A, но не
закрыл. Это прямо противоречит описанию «приход и излишек общие для всех строк
одного сырья».

Тесты покрывают случай, когда у обеих строк есть потребность в одном месяце, и
случай, когда излишек остаётся у той же строки, у которой есть следующий месяц.
Случай «излишек у одной строки, потребность у другой» не покрыт.

### 3.3. Удаление альтернативы молча теряет привязку поступления

При сохранении плана удалённые альтернативы удаляются без проверки связанных
поступлений. Внешний ключ `batch_items.purchase_plan_item_id` — `ON DELETE SET NULL`,
поэтому поступление остаётся, но его привязка становится пустой; факт по плану
падает, например, с 12 до 0. Никакого 409 и предупреждения нет.

Для основных строк такая защита есть (нельзя удалить связанную строку), для
альтернатив — нет. Это же работает и при удалении основной строки: её альтернативы
удаляются, даже если на них есть поступления. `delete_plan` при этом проверяет все
строки, включая альтернативы, — то есть поведение ещё и непоследовательно.

### 3.4. Потеря правок при одновременном сохранении

Сохранение плана — полная замена набора строк. Версии/ETag/`If-Match` нет: сервер
верит, что клиент прислал актуальный список. Два пользователя (или две вкладки):

1. оба открыли план с одной строкой;
2. первый добавил вторую строку и сохранил;
3. второй сохранил свою старую форму — его запрос содержит только первую строку.

Оба получат 200, но вторая строка первого будет удалена, а количество первой
вернётся к старому. Блокировка сериализует запросы, но не обнаруживает, что форма
устарела. Это не «смесь версий», а потеря уже сохранённых данных.

### 3.5. Отправка и утверждение работают с сохранённой версией, а не с экраном

Кнопка «Отправить на согласование» не сохраняет черновик: она отправляет то, что
уже лежит на сервере. Если закупщик поправил количество или добавил строку и сразу
нажал «Отправить», изменения не попадут в план; после ответа интерфейс перезагрузит
старые данные. Проверка цены при этом идёт по черновику на экране, поэтому возможны
и ложные 400 («укажите цену», хотя в плане цена есть), и отправка пустого плана,
если все строки есть только в черновике. Аналогично исполнительный директор может
утвердить старую версию.

### 3.6. API разрешает циклы, вложенность и «альтернативу самой себе»

Проверка альтернативы смотрит на **старое** состояние из БД, а не на то, что
сохраняется в этом же запросе. Поэтому через API можно:

- сделать две основные строки альтернативами друг друга (цикл);
- сделать строку альтернативой самой себе;
- сделать альтернативу у альтернативы;
- перенести основную строку в другую позицию плана продаж, оставив альтернативу
  привязанной к ней.

После такого сохранения `items` в ответе может быть пустым (в выборку попадают
только основные строки и их альтернативы), хотя строки в БД есть. Следующее
сохранение из интерфейса отправит пустой список и удалит их. Через кнопки UI это
не воспроизводится, но API — часть продукта, и дыру нужно закрыть.

### 3.7. Интерфейс и API считают покрытие двумя разными реализациями

На сервере есть `schedule`/`carry_forward`/`used_quantity`, но интерфейс их не
использует: он заново считает покрытие в `coverDrafts`. Уже есть расхождение:
для позиции, исчезнувшей из плана продаж, сервер отдаёт пустой `schedule`, а UI
берёт старые месяцы из `positions` и рисует старый график. Любая правка формулы
теперь требует синхронной правки в двух местах; округления тоже могут разойтись.

Там же: подписи «кг» зашиты в тексте, хотя у сырья может быть «шт» или «л».
Единицы основного и альтернативного сырья не сверяются, а котёл суммирует их как
одно число.

### 3.8. Остальное, что нашлось

- **Дубли строк.** Две одинаковые строки (то же сырьё, страна, позиция) разрешены и
  просто складываются: потребность удваивается. Контракт разрешает несколько строк,
  но от случайного двойного клика «+ Добавить сырьё» защиты нет.
- **Огромные числа.** В схеме нет верхней границы количества/цены; при вводе больше
  `Numeric(15,3)` БД падает, API отдаёт 500 вместо 400.
- **Год поступления не проверяется.** Поступление 2027 года можно привязать к плану
  2026; оно попадёт в декабрь 2026 и завысит покрытие.
- **Новую привязку можно поставить на неутверждённый план** через API (UI предлагает
  только утверждённые). Существующую привязку после возврата плана в работу сохранять
  можно — это разные случаи, и сейчас они не различаются.
- **`acknowledge-source` не проверяет статус плана:** через API можно «принять
  изменения» у утверждённого плана, хотя UI прячет кнопку и по процессу нужен
  пересмотр/возврат в работу.
- **Срок доставки не является одноразовым снимком:** при каждом сохранении плана
  `delivery_days` перезаписывается текущим значением страны, даже если страну не
  меняли. Правка справочника + любое сохранение меняет график у всех строк.
- **`updated_at` плана не меняется при правке строк** (меняются только дочерние
  записи). Если использовать его как версию для защиты от потери правок, сейчас он
  не подходит.
- **Причины возврата/пересмотра не видны:** они пишутся в `plan.notes`, но страница
  плана это поле не показывает.
- **В API `carry_forward` — общий излишек семейства, повторённый в каждой строке.**
  Суммировать его по строкам нельзя; в UI для групп это скрыто, для API — нет.
- **«Наличие» — это только привязанные приходы.** Остатки склада в плане не
  участвуют (загрузку остатков убрали), списаний/расхода нет. Сырьё, лежащее на
  складе, альтернативу не заменяет.
- **Гранулярность — месяц.** Даты внутри месяца не учитываются: приход 31-го
  заменяет альтернативу, израсходованную на потребность 1-го, и наоборот.
- **Мёртвый код/устаревшие комментарии:** `opening` в `cover_family` не передаётся,
  комментарий про остатки и `cover_group` в docstring уже не соответствуют
  поведению.

## 4. Гонки и целостность

Что защищено:

- `SELECT … FOR UPDATE` на строке плана в правке, отправке, утверждении, возврате,
  удалении и при привязке поступления;
- блокировка партии при правке/растаможке/удалении;
- уникальность года плана — при гонке создания один запрос получает 409;
- связанную основную строку нельзя удалить/сменить сырьё (409);
- план с любыми связанными поступлениями нельзя удалить.

Что осталось:

- **Потеря правок** при полной замене (3.4) — блокировка не помогает, нужна версия.
- **Удаление альтернативы vs привязка поступления**: обе операции берут блокировку
  плана и сериализуются, но удаление альтернативы не проверяет ссылки, поэтому
  существующая привязка всё равно молча обнуляется. Прежний QA-вывод «привязка к
  удаляемой строке без потерь» верен только для основных строк.
- **Пересмотр плана продаж во время отправки**: `_ensure_source_acknowledged`
  проверяет изменение, но не блокирует годовой план. Между проверкой и коммитом
  менеджер может утвердить новый план продаж — план закупок будет отправлен/утверждён
  со старым источником. Окно небольшое, но оно есть.
- **Сериализация ответа — несколько запросов без единого снимка**: `_serialize`
  несколько раз считает потребность и состояние источника. При параллельном
  утверждении плана продаж ответ может смешать старую и новую потребность.
- `update_items` удаляет альтернативы до проверки связанности основных строк;
  сейчас выручает откат сессии при исключении, но полагаться на это в сервисе не
  стоит.

## 5. Порядок исправлений

1. **Ядро покрытия.** Перебирать все месяцы, где есть потребность **или приход**;
   суммировать наличие **всех** основных строк за месяц, а не только тех, у которых
   в этом месяце есть потребность; остаток переносить между позициями и месяцами;
   альтернативы — только после исчерпания общего остатка. Добавить тесты:
   «приход в месяц без потребности», «излишек A закрывает февраль B», «приход после
   последнего месяца», «декабрь предыдущего года при потребности в марте».
2. **Автоподхват поступлений.** Решить, как приходы попадают в план: автоматически
   по сырью+году при загрузке/создании или учётом непривязанных приходов; не терять
   привязки при повторной загрузке «Партии». Это обязательное условие требования 2.
3. **Альтернативы без основной строки.** Разрешить альтернативе жить самостоятельно
   (при удалении основной — повышать одну из альтернатив до основной или оставлять
   её отдельной строкой). Защитить связанные альтернативы от удаления. Закрыть
   циклы/вложенность/self-reference проверкой **нового** состояния, а не старого.

## Статус после правок (2026-11-01)

Исправлено и покрыто тестами:

- **3.1 и 3.2 (ядро покрытия).** Расчёт перебирает все месяцы, где есть потребность
  или приход; приход в месяц без потребности ждёт ближайшую; запас любой основной
  строки закрывает потребность другой, даже если у неё в этом месяце нет
  потребности; приход после последнего месяца попадает в излишек. То же
  пересчитано в интерфейсе; добавлены unit- и API-тесты на оба сценария.
- **2.2 (автоподхват).** Загрузка позиций файлом «Партия» сама ставит привязку на
  первую строку утверждённого плана того же сырья и года (основную, если есть).
  Если плана/строки нет — привязки нет; ручную можно снять/сменить. Покрыто
  тестами, включая «план ещё черновик» и «другое сырьё».
- **2.4, 3.3, 3.6 (альтернативы).** Удаление любой связанной строки, включая
  альтернативу, — 409 (привязка поступления больше не теряется). Циклы,
  вложенность, self-reference, перенос основной строки в другую позицию и разные
  единицы измерения отклоняются проверкой по новому состоянию. При удалении
  основной строки одна альтернатива становится основной и получает объём
  удалённой (если единицы совпадают), остальные остаются под ней.
- **3.4 и 3.5 (потеря правок).** Сохранение принимает `version` (последний
  `updated_at`) и отвечает 409 на устаревшую форму; интерфейс отправляет version.
  «Отправить на согласование» сначала сохраняет строки с экрана, потом отправляет.
- **3.7 (часть).** Подписи единиц берутся из строки, а не «кг»; сервер для
  исчезнувшей позиции показывает те же месяцы снимка, что и интерфейс.
- **3.8 (часть).** Верхняя граница количества/цены — 422 вместо 500; ссылка на
  план другого года отклоняется (кроме пограничных декабря/января); новый
  `acknowledge-source` у утверждённого плана — 409; срок доставки не
  перезаписывается при правке справочника; причины возврата видны в карточке;
  полные дубли строк отклоняются.

Осталось (сознательно не в этом заходе):

- **2.1.** Плановый объём основного сырья по-прежнему вводится вручную: признака
  «основное сырьё для продукта» и BOM нет; автоматически распределяются только
  приходы.
- Автоподхват работает при загрузке файла «Партия»; позиции, добавленные вручную,
  и поступления, пришедшие до утверждения плана, автоматически не привязываются —
  нужна ручная привязка или повторная загрузка. Обратного backfill нет.
- `version` необязателен для внешних API-клиентов (UI его шлёт); без него защита от
  потери правок не включается.
- Гонка «пересмотр плана продаж во время отправки» и чтение ответа несколькими
  запросами без единого снимка остаются.
- Интерфейс всё ещё дублирует расчёт покрытия (`coverDrafts`), хотя теперь совпадает
  с сервером; единый источник не сделан.
- `carry_forward` в API — общий излишек семейства, повторённый в каждой строке;
  остатки склада и списания в плане не учитываются; гранулярность — месяц.
- Живой UI/e2e на стенде не прогонялся.
