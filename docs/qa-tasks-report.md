## 2. Дефекты

Порядок — как я предлагаю чинить. S1 — порча данных, S2 — неверные даты или
адресаты, S3 — мелочи и спорные правила.

### D1 (S2). Пустое название задачи и этапа
B3a, C13. Название из одних пробелов принимается: `201` у задачи, `200` у этапа.
В Ганте появляется строка без названия, найти её и открыть можно только по ссылке.
**Причина:** проверка «не короче 1 символа» до обрезки пробелов.
**Чинить:** проверять название после `strip()`, пустое — `422`.

### D2 (S2). Новый исполнитель не узнаёт о передаче задачи
J5, J1, A10. После смены исполнителя сообщение получает **прежний** исполнитель
(и его ссылка ведёт в задачу, куда ему уже нельзя — `403`), а новый — ничего.
**Причина:** в `update_task` адресаты берутся из старой связи `task.assignee`,
которая не обновляется при смене `assignee_id`.
**Чинить:** адресовать сообщение явно новому исполнителю; прежнему — отдельное
«вы сняты с задачи» (N4).

### D3 (S2). Снятие уже выполненной зависимости отбрасывает срок назад
H22. Задача стояла 22.11–29.11, мастер закрыт; после снятия зависимости старт
стал 02.11–09.11 (сегодня).
**Причина:** при снятии берётся «плавающая» дата, а невыполненных мастеров уже
нет — ориентиром становится сегодня.
**Чинить:** если задача не заблокирована, ничего не сдвигать.

### D4 (S2). Удаление мастера или его этапа молча меняет даты зависимой
H15, H16. Зависимая стояла 04.11–11.11; после удаления мастера (или этапа)
прыгнула на 22.11–29.11 — старый план — без сообщения.
**Причина:** зависимость удаляется каскадом, фиксация даты и сообщение не
выполняются.
**Чинить:** перед удалением зафиксировать дату остановки и отправить N2/N3.

### D5 (S2). Повторное открытие мастера откатывает дату зависимой
H23. Зависимая зафиксирована на 02.11; после возврата мастера в работу её старт
снова поехал — 01.11, и она опять «ждёт».
**Чинить:** не переводить уже стартовавшую зависимую обратно в плавающий режим;
сообщать о повторной блокировке.

### D6 (S1). Гонка создаёт замкнутый круг зависимостей
L6. Два одновременных запроса A→B и B→A прошли оба: у каждой задачи по
зависимости, обе навсегда заблокированы, отчёты не принимаются.
**Чинить:** проверять цикл в транзакции с блокировкой задач (или уникальный
индекс + повторная проверка после вставки).

### D7 (S2). Два одновременных отчёта по одному этапу
L5. Оба запроса приняты: два отчёта на один этап, шкала пересчитана дважды.
**Чинить:** уникальность «один промежуточный отчёт на этап» на уровне базы.

### D8 (S2). Параллельные загрузки обходят лимит файлов
E13. Одиннадцать одновременных загрузок — одиннадцать файлов при лимите 10.
**Чинить:** блокировка отчёта на время подсчёта и вставки.

### D9 (S3, нужно решение). Финальный отчёт при открытых этапах
D7, H17. Задача становится «Выполнена» и 100 %, открытый этап остаётся; если от
этого этапа зависели другие — они висят вечно.
**Предложение:** не принимать финальный отчёт, пока есть открытые этапы, либо
спрашивать «закрыть этапы вместе с задачей».

### D10 (S3). Возврат в работу показывает 100 %
D15. После возврата в базе 90 %, а шкала выводит 100 % (из последнего отчёта).
**Чинить:** убрать мёртвое присваивание 90 или показывать «возвращена в работу»
отдельной плашкой.

### D11 (S3). Двойной клик создаёт две задачи
B9. Два одинаковых запроса — две задачи.
**Чинить:** блокировать кнопку на время отправки.

### D12 (S3). Правка только описания присылает «Задача изменена»
J3. Шум для исполнителя: описание поменяли, сроки — нет.
**Чинить:** не отправлять сообщение, если менялось только описание.

### D13 (S3). Этап в задаче с плавающим стартом не сохраняется по датам с экрана
C14. Экран показывает 03.11–07.11, пользователь ставит этап 04.11–05.11 —
`422 «выходит за сроки»`: проверка идёт по плановым 08.11–12.11.
**Чинить:** проверять этапы по тем датам, которые видит пользователь.

### D14 (S3, нужно решение). Заблокированная задача и фильтр «просроченные»
I13. План задачи в прошлом, но она ждёт мастера — в «просроченные» не попадает.
Считаю правильным, но нужно подтвердить: у неё отдельный бейдж «ждёт».
