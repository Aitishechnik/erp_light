# Контракт данных: служебные сообщения и журнал действий

Статус: **черновик на согласование** (2026-10-27). Код пишем после подтверждения.

> **Версия 1 реализована (2026-10-27).** Согласовано: начинаем с критических
> событий и только для исполнительного директора. В коде — таблицы
> `audit_events` и `audit_event_reads`, каталог из 22 критических событий,
> колокольчик, страница «Служебные сообщения», запись событий из сервисов
> планов и итогов месяца и из API справочников/поступлений. Рабочие (info)
> события в каталог заведены, но пока не пишутся — это следующий этап.
> Список типов по ролям — [`service-messages-catalog.md`](service-messages-catalog.md).

## 1. Задача и границы

Нужны две вещи, которые живут в одной таблице событий:

* **журнал действий** — полный след того, кто и что сделал (включая вход, просмотр
  отчётов не пишем — только изменения);
* **служебные сообщения** — подмножество журнала: значимые изменения, которые
  показываются в «колокольчике» в углу экрана и адресованы конкретным ролям.
  Колокольчик показывает **только непрочитанные**; прочитанные и все действия
  остаются в журнале «Служебные сообщения».

Границы: почты, пуш-уведомлений, эскалаций по таймеру и «прочитано другими»
в этот этап не входит.

## 2. Что уезжает из интерфейса в сообщения

Разовые уведомления о результате действия (после действия они больше не нужны
на экране, а в журнале остаются историей):

| Где сейчас | Что уходит |
|---|---|
| «Загрузка данных» | «Создано: N, обновлено: M», ошибки файла |
| «Планирование продаж» | «План сохранён», «Корректировка утверждена — годовой план требует повторного согласования» |
| «Годовой план отдела» | «Отправлено на согласование», «Согласовано/отклонено» |
| «План закупок сырья» | «План сохранён», «Запрошен пересмотр», «Принято к сведению» |
| «Итоги месяца» | «Созданы черновики корректировок», «Месяц закрыт/открыт», решение месяца |
| «Поступления» | «Поступление создано/изменено/удалено», «Растаможено» |
| «Номенклатура», «Контрагенты», «Страны» | «Создано/изменено/удалено» |

**Остаётся на экране:** подсказки о текущем состоянии (что можно и нельзя сейчас),
ошибки заполнения форм и подтверждения («Удалить?») — это не сообщения, а часть формы.

## 3. Модель данных

### `audit_events` — журнал (одна строка = одно действие)

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid | ключ |
| `created_at` | timestamptz | когда |
| `actor_id` | uuid → users, nullable | кто; null — система |
| `actor_role` | varchar(32) | роль на момент действия (снимок) |
| `action` | varchar(64) | код события (см. §4) |
| `level` | varchar(16) | `info` или `critical` |
| `entity_kind` | varchar(32) | `sales_plan`, `purchase_plan`, `month`, `batch`, `product`, `counterparty`, `country`, `user`, `import`, `message` |
| `entity_id` | uuid, nullable | на что |
| `entity_label` | varchar(255) | человекочитаемо: «Менеджер по продажам (демо), 2027», «ИТ-2027-0004» |
| `summary` | text | одна строка для списка |
| `payload` | jsonb | подробности (было/стало), не показывается в списке |
| `year`, `month` | int, nullable | период, если событие привязано к месяцу |
| `is_message` | bool | показывать в колокольчике |
| `audience` | jsonb | список ролей, кому видно; `["all"]` — всем |

Индексы: `(created_at desc)`, `(action)`, `(entity_kind, entity_id)`,
`(is_message, created_at desc)`.

### `audit_event_reads` — кто прочитал сообщение

`event_id` + `user_id` (пара — ключ), `read_at`. Для журнала не нужна: журнал
читают целиком, «непрочитанных» в нём нет.

## 5. Кто что видит

| Роль | Сообщения |
|---|---|
| Исполнительный директор | **все** (и critical, и info) |
| Коммерческий директор | планы продаж и корректировки, годовой план, итоги месяца, клиенты, загрузка продаж |
| Директор по закупкам | план закупок, поступления, страны, справочники номенклатуры |
| Менеджер по закупкам (импорт) | поступления, партии, номенклатура, загрузки |
| Менеджер по продажам | свои планы и корректировки, свои клиенты, свои строки итогов месяца |

«Свои» определяется по `actor_id`/`manager_id`, а не по роли — менеджер не видит
чужих сообщений. Проверка — на сервере, а не в интерфейсе.

## 6. API

| Метод | Что |
|---|---|
| `GET /messages` | сообщения текущего пользователя: `unread`, `limit` (по умолчанию 20), `before` (курсор) |
| `GET /messages/count` | `{"unread": N}` |
| `POST /messages/read` | `{"ids": [...]}` — отметить прочитанными |
| `POST /messages/read-all` | отметить все |
| `GET /audit` | журнал: `action`, `entity_kind`, `entity_id`, `limit`, `before` |
| `GET /audit/cleanup` | предложение очистки: `{year, events}` или `null` |
| `POST /audit/cleanup` | `{"year": 2025}` — удалить записи за календарный год (только ГД) |

Реализовано ровно так, за вычетом `level`/`actor_id`/`year`/`month` в фильтрах
журнала — их добавим, когда появится страница с расширенными фильтрами.

Права: `GET /audit` — исполнительный директор видит всё, остальные — свои действия
и события, адресованные им (`audience` содержит `user:<id>`). `GET /messages` —
каждый свои.

## 6.1 Ссылка на объект и очистка (реализовано 2026-10-27)

* В ответе сообщений и журнала есть `link` — адрес вида `#/month/2027/1`.
  Формируется из `action`/`entity_kind`/`year`/`month`/`entity_id`.
* Интерфейс понимает адреса `#/<раздел>/<параметры>`; раздел открывается сразу
  на объекте, строка (номенклатура, контрагент, страна) подсвечивается, а
  поступление открывается карточкой.
* Очистка: с марта каждый месяц предложение удалить журнал за прошлый
  календарный год; удаление только по подтверждению ГД. Удаляются строки
  `audit_events` за период, отметки прочтения уходят каскадом.

## 7. Интерфейс

* **Колокольчик** — в шапке панели профиля (справа снизу), значок + счётчик
  непрочитанных; клик открывает панель с последними 20 сообщениями, кнопками
  «Отметить всё прочитанным» и «Весь журнал».
* **Панель** — строка: время, кто, что (одна строка), ссылка «Открыть» на объект
  (план, месяц, поступление), цвет по уровню.
* **Страница «Служебные сообщения»** (`Администрирование → Служебные сообщения`) —
  полный журнал с фильтрами по типу, уровню, роли, периоду и поиском.
* Уведомления на экране заменяются, а не дублируются: после действия экран
  обновляет состояние, а текст результата уходит в колокольчик.

## 8. Этапы

1. **Бэкенд:** таблицы, сервис `audit_service.record(...)`, вызовы из сервисов
   домена, API сообщений и журнала, права, тесты (событие пишется на каждое
   действие; чужой менеджер своих сообщений не видит).
2. **Интерфейс:** колокольчик + панель + страница журнала; убрать разовые
   уведомления из перечисленных в §2 экранов; тесты и e2e.
3. **Тест на стенде 2027:** пройти месяц и посмотреть, что пришло директору,
   менеджеру и закупщику.
4. **Список типов сообщений по ролям** — таблица из §4–5 доводится до финального
   вида и попадает в `docs/` для продакт-менеджера.

## 6.3 Колокольчик — только непрочитанное (2026-11-02)

* Панель запрашивает `GET /messages?unread=true&limit=20`, поэтому показывает
  только непрочитанные; счётчик в заголовке — сколько их всего.
* Клик по сообщению отмечает его прочитанным и убирает из панели; «Отметить всё»
  очищает список; пусто — «Непрочитанных нет — все сообщения в журнале».
* Прочитанное не теряется: журнал отдаёт и свои действия, и адресованные события,
  поэтому менеджер видит в нём сообщения от директора. Чужие — нет, ГД видит всё.
