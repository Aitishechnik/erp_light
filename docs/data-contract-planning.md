# Контракт данных: планирование

Согласовано с продукт-менеджером 2026-10-07 (перед кодом — правило SLOW TRACK).
Реализация плана закупок — следующий шаг; здесь зафиксирован весь контракт целиком.

## 1. Роли (5)

| Роль (код) | Кто это |
|---|---|
| `sales_manager` | Менеджер по продажам |
| `commercial_director` | Коммерческий директор |
| `purchase_director` | Директор по закупкам |
| `import_manager` | Менеджер по закупкам (импорт) |
| `executive_director` | Исполнительный директор (аналог ген. директора) |

Вход — логин и пароль (pbkdf2-хеш, cookie-сессия). Демо-пользователи создаются
командой `cd backend && make seed-users` (по одному на роль).

## 2. Годовой план продаж

**Документ** — один план на пару «год + менеджер» (уникальность в БД).
План создаёт сам менеджер (на себя) или коммерческий директор (на любого менеджера).

| Часть | Поля |
|---|---|
| Шапка | год, менеджер, автор, статус, примечания, даты создания/изменения |
| Строка | клиент, товар, месяц (1–12), количество, цена за единицу, примечание |

- Строка = **клиент × товар × месяц**; цена одна на строку плана и разносится по всем месяцам.
- Уникальность строки — «план + клиент + товар + месяц» (один товар для двух клиентов —
  это две разные строки).
- Сумма строки = количество × цена; сумма плана — сумма строк.
- Клиент обязателен: строка без клиента не сохраняется. Клиент должен быть активным.

**Цепочка статусов:** `draft` (черновик) → `filling` (заполняется) →
`on_review` (на проверке) → `approved` (утверждён).

| Переход | Кто | Условие |
|---|---|---|
| Создать | менеджер (свой) / коммерческий директор | один план на год и менеджера |
| Сохранить строки | владелец-менеджер / коммерческий директор | только редактируемые месяцы |
| Отправить на заполнение | коммерческий директор | из черновика |
| Отправить на проверку | владелец-менеджер | из черновика/заполняется, план не пустой |
| Утвердить / вернуть на доработку | коммерческий директор | из «на проверке»; возврат пишет причину в примечания |
| Удалить | коммерческий директор / владелец | только черновик или «заполняется» |

Правка утверждённого плана коммерческим директором возвращает его на проверку.

**Заморозка (по серверной дате, ничего не храним):** год меньше текущего — заморожены
все 12 месяцев; текущий год — месяцы строго до текущего; будущий год — редактируется
весь. Запрос с замороженными месяцами отклоняется целиком (HTTP 409), а не «молча
сохраняется частями». Поле `editable_months` в ответе API говорит фронту, что можно править.

**Видимость:** менеджер видит только свои планы; коммерческий и исполнительный
директора — все. Роли закупок к планам продаж доступа не имеют (403).

## 3. Справочники (номенклатура и клиенты)

**Номенклатура** (`products`): код (артикул, уникален), наименование, вид
(`goods` — товар, `material` — материал), единица измерения, признак «активна».
Позиции заводятся вручную на экране «Номенклатура», а также автоматически — при
загрузке партий из 1С. В плане продаж выбираются только активные позиции.

**Клиенты** (`clients`): наименование (уникально), ИНН (необязательно), примечание,
признак «активен». Один справочник — только клиенты; **поставщики по решению
продукт-менеджера будут отдельным справочником** вместе с планом закупок.

Кто меняет справочники: менеджер по продажам, коммерческий директор, директор по
закупкам. Читать может любой вошедший; менеджер по закупкам (импорт) справочники
только читает.

## 4. План закупок (следующий шаг, контракт уже согласован)

- Документ — один актуальный план на год; создаёт директор по закупкам, утверждает
  исполнительный директор (в erp_v2 такого звена не было — это новое требование).
- Строка = товар × месяц потребности: количество к заказу, цена, поставщик, срок
  логистики, месяц заказа = месяц потребности − ceil(срок логистики / 30), минимум 1.
- Источник потребности — **все утверждённые** планы продаж года, агрегация по
  «товар × месяц», минус складской остаток (месяцы закрываются по порядку 1→12).
- Правки менеджера по закупкам (импорт): количество, цена, поставщик, срок.
- Кнопка «пересчитать» переписывает черновик по свежим утверждённым планам продаж.

## 5. Что сознательно НЕ переносим из erp_v2

Производственную разузловку (BOM) — закупаем напрямую; версии плана и «отпечатки»
источников; мультиорганизационность и вес/тару; единый справочник контрагентов
(клиенты отдельно, поставщики — отдельным справочником позже); заказы поставщику и
экспорт в 1С; отдельную таблицу согласования и аудит переходов.

## 6. Технические детали

- Деньги и количество — `Numeric`/`Decimal`; в JSON уходят **строкой** (правило проекта).
- Таблицы: `users`, `auth_sessions`, `products`, `clients`, `sales_plans`, `sales_plan_items`.
- Эндпоинты: `POST /api/v1/auth/login|logout`, `GET /api/v1/auth/me`, `GET /api/v1/users`,
  `GET|POST /api/v1/products`, `PATCH /api/v1/products/{id}`,
  `GET|POST /api/v1/clients`, `PATCH /api/v1/clients/{id}`,
  `GET|POST /api/v1/sales-plans`, `GET /api/v1/sales-plans/{id}`,
  `PUT /api/v1/sales-plans/{id}/items`,
  `POST /api/v1/sales-plans/{id}/send-to-fill|submit|approve|reject`,
  `DELETE /api/v1/sales-plans/{id}`.
- Данные остальных разделов (`/stock`, `/batches`, `/products`) закрыты входом.
