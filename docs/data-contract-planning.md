# Контракт данных: планирование

Согласовано с продукт-менеджером 2026-10-07 (перед кодом — правило SLOW TRACK).
План закупок сырья уточнён 2026-10-21 (позже): строится из финально согласованного
годового плана продаж, сырьё раскладывается вручную, материалы не планируются.
Здесь зафиксирован весь контракт целиком.

## 1. Роли (5)

| Роль (код) | Кто это |
|---|---|
| `sales_manager` | Менеджер по продажам |
| `commercial_director` | Коммерческий директор |
| `purchase_director` | Директор по закупкам |
| `import_manager` | Менеджер по закупкам (импорт) |
| `executive_director` | Исполнительный директор (аналог ген. директора) |

Вход — логин и пароль (pbkdf2-хеш, cookie-сессия). Демо-пользователи создаются
командой `cd backend && make seed-users` (по одному на роль).

## 2. Годовой план продаж

**Документ** — один план на пару «год + менеджер» (уникальность в БД).
План создаёт сам менеджер (на себя) или коммерческий директор (на любого менеджера).

| Часть | Поля |
|---|---|
| Шапка | год, менеджер, автор, статус, примечания, даты создания/изменения |
| Строка | клиент, товар, месяц (1–12), количество, примечание |

- Строка = **клиент × товар × месяц**, планируется **только количество**.
- **Цен в плане продаж нет** (решение продукт-менеджера 2026-10-07, позже):
  деньги живут в матрице ценообразования, в закупках и себестоимости. Поэтому
  «Сумма» и «Всего по плану» в интерфейсе отсутствуют; у строки показывается
  итог по количеству в её единице измерения (шт, кг, л).
- Уникальность строки — «план + клиент + товар + месяц» (один товар для двух клиентов —
  это две разные строки).
- Клиент обязателен: строка без клиента не сохраняется. Клиент — активный контрагент
  с признаком «покупатель».

**Цепочка статусов:** `draft` (черновик) → `filling` (заполняется) →
`on_review` (на проверке) → `approved` (утверждён).

| Переход | Кто | Условие |
|---|---|---|
| Создать | менеджер (свой) / коммерческий директор | один план на год и менеджера |
| Сохранить строки | владелец-менеджер / коммерческий директор | только редактируемые месяцы |
| Отправить на заполнение | коммерческий директор | из черновика |
| Отправить на проверку | владелец-менеджер | из черновика/заполняется, план не пустой |
| Утвердить / вернуть на доработку | коммерческий директор | из «на проверке»; возврат пишет причину в примечания |
| Удалить | коммерческий директор / владелец | только черновик или «заполняется» |

Правка утверждённого плана коммерческим директором через API возвращает его на
проверку; в интерфейсе утверждённый план read-only, штатный путь — корректировка (§2.2).

**Заморозка (по серверной дате, ничего не храним):** год меньше текущего — заморожены
все 12 месяцев; текущий год — месяцы строго до текущего; будущий год — редактируется
весь. Запрос с замороженными месяцами отклоняется целиком (HTTP 409), а не «молча
сохраняется частями». Поле `editable_months` в ответе API говорит фронту, что можно править.

**Видимость:** менеджер видит только свои планы; коммерческий, исполнительный
директора и директор по закупкам — все (закупки только читают). Менеджер по закупкам
(импорт) видит планы на чтение.

### 2.1. Годовой план отдела продаж

Согласовано с продукт-менеджером 2026-10-21. Планы менеджеров — по-прежнему
ответственность коммерческого директора, но **финальную версию** утверждает
генеральный директор (в erp_lite это роль `executive_director`).

- Документ — **один на год** (`sales_plan_approvals`), собирается из утверждённых
  планов всех **активных** менеджеров по продажам. Если у кого-то из них нет
  утверждённого плана, отправка блокируется (409 со списком менеджеров).
- Статусы: `draft` (не отправлен) → `on_review` (на финальном согласовании) →
  `approved` (финально согласован) / `revision` (требует повторного согласования).
- Отправляет коммерческий директор; утверждает, возвращает и снимает с утверждения
  только генеральный директор. Коммерческий директор утвердить годовой план не может.
- **Любое изменение любого плана менеджера** — правка строк, повторное утверждение,
  корректировка, новый план нового менеджера — снимает финальное согласование: годовой план
  переходит в `revision`. Коммерческий директор отправляет его заново, ГД утверждает
  заново.
- `source_hash` — отпечаток состава и количеств утверждённых планов на момент
  отправки/утверждения. Если данные разошлись с отпечатком, утверждение недействительно
  (409 при попытке утвердить), даже если статус остался `approved`.
- Видят годовой план: коммерческий отдел (менеджеры по продажам и коммерческий
  директор), генеральный директор и директор по закупкам; менеджеры и закупки —
  только чтение.

### 2.2. Корректировка утверждённого плана менеджера

Согласовано с продукт-менеджером 2026-10-23: корректировка — **полная
редактируемая копия** плана, а не список точечных изменений.

- Утверждённый план **не правится напрямую**. Корректировка — это копия строк плана
  на редактируемые месяцы (клиент × товар × месяц → количество), которую можно
  менять как обычный план: править объёмы, **добавлять и удалять клиентов, товары и
  позиции**. Список изменений «было/стало» формируется из копии и исходного плана.
- Создать корректировку может владелец-менеджер, **коммерческий директор** (любого
  утверждённого плана) и **исполнительный директор** (предложить конкретные
  корректировки). Черновик правят все, кому доступна корректировка; коммерческий
  директор может править черновик менеджера.
- Черновик **отправляется** коммерческому директору, тот утверждает (строки
  редактируемых месяцев заменяются строками корректировки, план остаётся
  утверждённым) или отклоняет с причиной; план при отклонении не меняется.
  Применить корректировку без отправки нельзя — в том числе коммерческому директору
  и исполнительному директору. Коммерческий директор утверждает и свою отправленную
  корректировку.
- Применение корректировки меняет утверждённый план → финальное согласование
  годового плана снимается (см. §2.1). ГД финально согласует изменённый план,
  повторно согласуя годовой план.
- Если план изменился с момента создания корректировки, применить её нельзя (409):
  корректировку нужно создать заново.
- Замороженные месяцы по-прежнему менять нельзя — ни менеджеру, ни коммерческому,
  ни исполнительному директору. Корректировка затрагивает только редактируемые
  месяцы; правила строк те же, что в §2.
- Открытая корректировка на план — одна (`draft` или `on_review`). История всех
  корректировок сохраняется: автор, статус, «было/стало», причина отклонения.
- В интерфейсе утверждённый план — **read-only** для всех: кнопка «Сохранить» не
  показывается, правка идёт только через блок корректировки. Корректировку создаёт
  владелец, коммерческий или исполнительный директор; коммерческий директор может
  править черновик менеджера.

## 3. Справочники (номенклатура и контрагенты)

**Номенклатура** (`products`): код 1С (уникален), наименование, вид
(`material` — материалы, `raw` — сырьё, `finished` — готовая продукция,
`goods` — прочие товары), единица измерения, источник (`1c`/`manual`), признак
«активна». Наполняется загрузкой выгрузок 1С; можно завести и вручную.

**Контрагенты** (`counterparties`): наименование (уникально с точностью до регистра
и пробелов), ИНН (необязательно), примечание, **три признака роли** — покупатель,
локальный поставщик, импортный поставщик, — источник и признак «активен».
Одна компания = одна запись: если она есть и среди покупателей, и среди поставщиков,
у записи стоят оба признака.

Кто меняет справочники: менеджер по продажам, коммерческий директор, директор по
закупкам. Читать может любой вошедший; менеджер по закупкам (импорт) справочники
только читает. Массовое наполнение — загрузкой файлов, см.
[`data-contract-imports.md`](data-contract-imports.md).

## 4. План закупок сырья

Согласовано с продукт-менеджером 2026-10-21, пересмотрено 2026-10-21 (позже):
план закупок строится **на основании финально согласованного годового плана продаж**.
Материалы не планируются, «обратного BOM» нет: позицию плана продаж закупщик
раскладывает на сырьё вручную, но позиции и количество приходят из плана продаж.

### 4.1. Страны и срок доставки

- Справочник **«Страны»** (`countries`): название (уникально без учёта регистра и
  лишних пробелов) и срок доставки в днях (1–365). Пункт меню
  «Справочники → Страны». Читать может любой вошедший, менять — директор по закупкам.
- Страна выбирается **в строке плана закупок**: одно и то же сырьё может ехать из
  разных стран. Срок доставки берётся из справочника, в строке показывается только
  для чтения и **фиксируется снимком** при сохранении, чтобы правка справочника не
  переписывала уже согласованные планы.
- Срок доставки сдвигает месяц заказа назад: **заказать до = месяц потребности −
  ceil(срок / 30)**. Дата заказа может попасть в предыдущий год (январь 2027 при
  сроке 90 дней — это октябрь 2026); в интерфейсе это «окт 2026», а не «месяц 1».
  Если срок заказа уже прошёл, месяц помечается «срок заказа прошёл».

### 4.2. Документ и строки

- Документ — **один план на год** (`purchase_plans`, уникальность по году).
  Создать его можно только при наличии **финально согласованного** годового плана
  продаж за этот год (иначе 409). Если годовой план ещё не согласован или ушёл в
  `revision`, создание блокируется.
- **Позиции** плана закупок — товары годового плана продаж; клиенты и менеджеры
  суммируются (позиция × месяц). Позиции с нулевым количеством не показываются.
- **Строка** (`purchase_plan_items`) = позиция плана продаж × сырьё × страна:
  годовое количество, цена ₽ (вводит закупщик), поставщик (необязательно),
  примечание. Строк на позицию — сколько угодно (разные страны, поставщики, цены).
- **Разбивка по месяцам** считается автоматически: годовое количество строки
  делится пропорционально продажам позиции по месяцам, остаток от округления
  отдаётся последнему месяцу, поэтому сумма месяцев равна годовому количеству.
  Цены и количества вводятся вручную; автоматического подбора цен нет.
- **Остатки не вычитаются** — это решение директора по закупкам, не расчёт.
- Несколько строк на одно сырьё и позицию разрешены.
- Если позиция исчезла из плана продаж, её строки не удаляются: группа остаётся с
  пометкой «позиции больше нет в плане продаж».
- Заморозка — по году: план прошлого года доступен только для чтения, текущего и
  будущего — редактируется (общее правило §2 на месяцы внутри года не применяется,
  потому что строки годовые).

### 4.3. Пересмотр плана продаж

- При создании плана закупок сохраняется **снимок источника**: позиция × месяц ×
  количество + отпечаток (`source_snapshot`, `source_hash`, `source_snapshot_at`).
- Если годовой план продаж пересмотрели и **заново финально согласовали**, при
  открытии плана закупок директор по закупкам видит расхождение: карточку
  «План продаж пересмотрен», таблицу «было → стало» по позициям и месяцам, метки
  «изменено» у затронутых позиций и кнопку **«Принять к сведению»**. Клиенты и
  менеджеры в diff не участвуют — только товар, месяц и количество.
- Пока изменения не приняты, план нельзя отправить на согласование и утвердить
  (409). «Принять к сведению» обновляет снимок и пишет событие в историю
  (`purchase_plan_source_events`), чтобы можно было вернуться и посмотреть, что
  именно изменилось.
- Пока годовой план находится в `revision`, план закупок показывает потребность по
  последней согласованной версии и мягкую строку «план продаж пересматривается»;
  diff не показывается, чтобы не дёргать директора черновиками и отклонёнными
  корректировками.
- Если план закупок уже утверждён, директор по закупкам нажимает **«Запросить
  пересмотр»**; исполнительный директор видит просьбу и возвращает план в работу.
  После правок план снова отправляется на финальное согласование ГД.

### 4.4. Согласование и роли

- Статусы: `draft` → `on_review` → `approved`; возврат на доработку — с причиной.
  Утверждённый план доступен только на чтение; вернуть в работу может
  исполнительный директор.
- Создают, правят и отправляют план директор по закупкам и менеджер по закупкам
  (импорт); удаляет только директор по закупкам и только черновик. Утверждает
  **исполнительный директор**; после пересмотра план согласуется им заново.
- Смотреть план могут эти две роли и исполнительный директор.
- Строки сохраняются целиком; при ошибке в любой строке не меняется ничего.

## 5. Что сознательно НЕ переносим из erp_v2

Производственную разузловку (BOM) — закупаем напрямую; версии плана и «отпечатки»
источников; мультиорганизационность и вес/тару; единый справочник контрагентов
(клиенты отдельно, поставщики — отдельным справочником позже); заказы поставщику и
экспорт в 1С; отдельную таблицу согласования и аудит переходов.
